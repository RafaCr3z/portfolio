Remediação closed-loop de configuration drift em FortiOS com NetBox

  • FortiOS 7.6.4
  • NetBox
  • n8n
  • Python · Netmiko
  • MongoDB
  • 19/20

Resumo: em 24 incidentes injetados em laboratório, o sistema corrigiu sozinho todas as 15 falhas lógicas, em 4 a 7 segundos por SSH e em menos de 2 segundos por transação via REST API. As falhas físicas foram detetadas em menos de 10 segundos e escaladas ao operador.

O problema

Em redes críticas do Estado com túneis VPN IPsec IKEv2 sobre circuitos MPLS, desvios manuais de configuração (gateway remoto, seletores CIDR da Phase 2, políticas de firewall) provocam quebras silenciosas. A triagem manual demora 15 a 30 minutos. O trabalho decorreu em duas fases, em parceria com a ARTE, I.P. (Agência para a Reforma Tecnológica do Estado, ex-AMA).

  • Projeto I (fev 2026), diagnóstico: topologia Hub-and-Spoke em VMware Workstation Pro com FortiOS 7.6.4, em 4 segmentos isolados (gestão OOB, WAN MPLS, túnel IPsec com IKEv2 AES256-SHA256 / DH 20, LAN do Spoke). Uma árvore de decisão no n8n correlaciona alertas do PRTG com consultas SSH para separar falhas físicas de erros lógicos e alertar por Telegram em menos de 3,2 s.
  • Projeto II (jun 2026), remediação: evolução para ciclo fechado com NetBox como fonte de verdade, motor de remediação híbrido (Netmiko por SSH e REST API CMDB do FortiOS), escalonamento automático ao operador WAN por email e auditoria em MongoDB + Metabase.

Arquitetura

  1. Deteção e pre-check ICMP. Um webhook do PRTG dispara quando o tráfego do túnel cai para 0 KB/s. Antes de qualquer ação, o n8n faz ping -c 2 -W 2 172.16.0.2. Se falhar, a causa é física (mpls_down ou power_or_hardware_failure) e não vale a pena tentar SSH ou API. Isto baixou o tempo de deteção de ~15 min para menos de 10 s.
  2. Fonte de verdade. O NetBox guarda a configuração esperada. O n8n consulta GET /api/dcim/devices/?name=FGT-HUB antes de alterar o equipamento.
  3. Remediação híbrida.
    • Fase 1, licença de avaliação: a licença trial do FortiGate-VM bloqueia escrita por HTTP. Contornei isso com scripts Python (remediate_config.py, remediate_phase2.py, remediate_tunnel.py) que corrigem por SSH via Netmiko, num virtualenv isolado no Ubuntu Server 24.04.
    • Fase 2, licença comercial: HTTP PUT direto na CMDB (/api/v2/cmdb/vpn.ipsec/phase1-interface/…, /api/v2/cmdb/firewall/policy/…), com token restrito a um único host de gestão. Menos de 2 s por transação.
  4. Auditoria. Cada incidente fica registado em MongoDB (incident_runs e incident_runs_enterprise), com alertas Telegram, tickets por email e painéis de MTTR em Metabase.

O que aprendi

  • Verificar a camada física primeiro poupa tempo e evita ações erradas: metade do valor está em saber quando não agir.
  • Ter uma fonte de verdade (NetBox) é o que torna a correção segura. Sem ela, o sistema não sabe qual é o estado certo.
  • Desenhar para restrições reais (a licença de avaliação) levou a um motor com dois caminhos, que é mais robusto do que só um.

Closed-loop remediation of configuration drift in FortiOS with NetBox

  • FortiOS 7.6.4
  • NetBox
  • n8n
  • Python · Netmiko
  • MongoDB
  • 19/20

TL;DR: across 24 incidents injected in the lab, the system fixed all 15 logical faults on its own, in 4–7 seconds over SSH and under 2 seconds per call via the REST API. Physical failures were detected in under 10 seconds and escalated to the carrier.

The problem

In public-sector networks running IPsec IKEv2 tunnels over MPLS circuits, manual configuration drift (remote gateway, Phase 2 CIDR selectors, firewall policies) causes silent outages. Manual triage takes 15 to 30 minutes. The work ran in two stages, in partnership with ARTE, I.P., Portugal's state agency for technology reform.

  • Project I (Feb 2026), diagnostics: hub-and-spoke topology in VMware Workstation Pro with FortiOS 7.6.4 across 4 isolated segments (OOB management, MPLS WAN, IPsec tunnel with IKEv2 AES256-SHA256 / DH 20, spoke LAN). An n8n decision tree correlates PRTG alerts with SSH checks to separate physical failures from logical errors, alerting via Telegram in under 3.2 s.
  • Project II (Jun 2026), remediation: closed loop with NetBox as the source of truth, a hybrid remediation engine (Netmiko over SSH and the FortiOS CMDB REST API), automatic email escalation to the WAN carrier, and auditing in MongoDB + Metabase.

Architecture

  1. Detection and ICMP pre-check. A PRTG webhook fires when tunnel traffic drops to 0 KB/s. Before doing anything, n8n runs ping -c 2 -W 2 172.16.0.2. If it fails, the cause is physical (mpls_down or power_or_hardware_failure) and there is no point trying SSH or the API. This cut detection time from ~15 min to under 10 s.
  2. Source of truth. NetBox holds the expected configuration. n8n queries GET /api/dcim/devices/?name=FGT-HUB before changing the device.
  3. Hybrid remediation.
    • Stage 1, evaluation licence: the FortiGate-VM trial licence blocks HTTP writes. I worked around it with Python scripts (remediate_config.py, remediate_phase2.py, remediate_tunnel.py) that fix the device over SSH via Netmiko, in an isolated virtualenv on Ubuntu Server 24.04.
    • Stage 2, commercial licence: direct HTTP PUT to the CMDB (/api/v2/cmdb/vpn.ipsec/phase1-interface/…, /api/v2/cmdb/firewall/policy/…) with a token restricted to a single management host. Under 2 s per call.
  4. Auditing. Every incident is recorded in MongoDB (incident_runs and incident_runs_enterprise), with Telegram alerts, email tickets and MTTR dashboards in Metabase.

What I learned

  • Checking the physical layer first saves time and prevents wrong actions: half the value is knowing when not to act.
  • A source of truth (NetBox) is what makes remediation safe. Without it, the system doesn't know what "correct" looks like.
  • Designing around a real constraint (the evaluation licence) produced a two-path engine, which is more robust than one.
