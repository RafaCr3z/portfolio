CI/CD sem segredos estáticos: GitHub Actions + Azure OIDC

  • GitHub Actions
  • azure/login@v2
  • Entra ID
  • Bicep
  • Checkov

Resumo: no projeto CityGuards, o pipeline de deploy autentica-se no Azure com tokens OIDC de curta duração. Não há nenhuma password ou chave de Service Principal guardada no repositório.

O risco

Guardar segredos de Service Principal de longa duração nos secrets do repositório é um dos vetores mais explorados em ataques à cadeia de fornecimento de software. Uma fuga num log de build ou um commit acidental dá acesso persistente à cloud, e obriga a rotações de emergência e auditorias.

A solução: confiança federada com OpenID Connect

  • Claims assinadas: o runner do GitHub pede um token OIDC (JWT) assinado com organização, repositório, branch (por exemplo refs/heads/main) e ambiente.
  • Troca de token (azure/login@v2): o Azure valida o emissor (https://token.actions.githubusercontent.com) e devolve um access token válido no máximo 60 minutos, limitado ao Resource Group do projeto.
  • Infraestrutura em Bicep: connection strings e chaves são injetadas em tempo de deploy com funções nativas como listKeys(), por isso nenhum valor sensível fica no código.
  • Checkov no pipeline: análise estática dos templates Bicep e Dockerfiles antes do deploy, para apanhar portas de gestão expostas, protocolos antigos ou permissões RBAC a mais.

Resultado

Zero credenciais de longa duração no repositório e cada operação no Azure Activity Log fica ligada ao commit e ao workflow do GitHub que a originou.

CI/CD without static secrets: GitHub Actions + Azure OIDC

  • GitHub Actions
  • azure/login@v2
  • Entra ID
  • Bicep
  • Checkov

TL;DR: in the CityGuards project, the deploy pipeline authenticates to Azure with short-lived OIDC tokens. No password or Service Principal key is stored in the repository.

The risk

Storing long-lived Service Principal secrets in repository secrets is one of the most exploited vectors in software supply chain attacks. A leak in a build log or an accidental commit gives persistent cloud access, forcing emergency rotations and audits.

The fix: federated trust with OpenID Connect

  • Signed claims: the GitHub runner requests a signed OIDC token (JWT) with organisation, repository, branch (e.g. refs/heads/main) and environment.
  • Token exchange (azure/login@v2): Azure validates the issuer (https://token.actions.githubusercontent.com) and returns an access token valid for at most 60 minutes, scoped to the project's Resource Group.
  • Infrastructure in Bicep: connection strings and keys are injected at deploy time with native functions such as listKeys(), so no sensitive value lives in the code.
  • Checkov in the pipeline: static analysis of Bicep templates and Dockerfiles before deploy, catching exposed management ports, outdated protocols or excessive RBAC permissions.

Outcome

Zero long-lived credentials in the repository, and every operation in the Azure Activity Log is traceable to the commit and GitHub workflow that triggered it.
