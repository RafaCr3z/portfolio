CI/CD sem segredos estáticos: GitHub Actions + Azure OIDC

  • GitHub Actions
  • azure/login@v2
  • Entra ID
  • Bicep
  • Trivy

Resumo: no CityGuards, depois da entrega académica, preparei o pipeline para se autenticar no Azure com tokens OIDC de curta duração, sem nenhuma password ou chave de Service Principal no repositório. Neste repositório público os identificadores do Azure não estão configurados, por isso o pipeline corre em modo de validação: compila o Bicep sem criar recursos.

O risco

Guardar segredos de Service Principal de longa duração nos secrets do repositório é um dos vetores mais explorados em ataques à cadeia de fornecimento de software. Uma fuga num log de build ou um commit acidental dá acesso persistente à cloud, e obriga a rotações de emergência e auditorias.

A solução: confiança federada com OpenID Connect

  • Claims assinadas: o runner do GitHub pede um token OIDC (JWT) assinado com organização, repositório, branch (por exemplo refs/heads/main) e ambiente.
  • Troca de token (azure/login@v2): o Azure valida o emissor (https://token.actions.githubusercontent.com) e devolve um access token válido no máximo 60 minutos, limitado ao Resource Group do projeto.
  • Infraestrutura em Bicep: o template (de base académica, escrito por um colega e adaptado por mim) é compilado com az bicep build em cada push, para apanhar erros antes de qualquer deploy.
  • Trivy no pipeline: análise de vulnerabilidades (CRITICAL e HIGH) às dependências e ao container. Por agora é informativa e não bloqueia o build; torná-la bloqueante é o passo seguinte.
  • Deploy condicional: o login com azure/login@v2 e o deploy só correm quando os três identificadores (client, tenant, subscription) existem. Sem eles, o pipeline faz um dry-run e termina com sucesso.

Resultado

Zero credenciais de longa duração no repositório. Com a federação configurada, cada operação no Azure Activity Log fica ligada ao commit e ao workflow do GitHub que a originou.

CI/CD without static secrets: GitHub Actions + Azure OIDC

  • azure/login@v2
  • Entra ID
  • Bicep

TL;DR: after the coursework, I set up the CityGuards pipeline to authenticate to Azure with short-lived OIDC tokens, with no password or Service Principal key in the repository. In this public repository the Azure identifiers are not configured, so the pipeline runs in validation mode: it compiles the Bicep without creating resources.

The risk

Storing long-lived Service Principal secrets in repository secrets is one of the most exploited vectors in software supply chain attacks. A leak in a build log or an accidental commit gives persistent cloud access, forcing emergency rotations and audits.

The fix: federated trust with OpenID Connect

  • Signed claims: the GitHub runner requests a signed OIDC token (JWT) with organisation, repository, branch (e.g. refs/heads/main) and environment.
  • Token exchange (azure/login@v2): Azure validates the issuer (https://token.actions.githubusercontent.com) and returns an access token valid for at most 60 minutes, scoped to the project's Resource Group.
  • Infrastructure in Bicep: the template (academic baseline written by a teammate, adapted by me) is compiled with az bicep build on every push, catching errors before any deploy.
  • Trivy in the pipeline: vulnerability scan (CRITICAL and HIGH) of dependencies and the container. For now it is informational and does not fail the build; making it blocking is the next step.
  • Conditional deploy: the azure/login@v2 login and the deploy only run when the three identifiers (client, tenant, subscription) exist. Without them, the pipeline does a dry run and succeeds.

Outcome

Zero long-lived credentials in the repository. With the federation configured, every operation in the Azure Activity Log is traceable to the commit and GitHub workflow that triggered it.
